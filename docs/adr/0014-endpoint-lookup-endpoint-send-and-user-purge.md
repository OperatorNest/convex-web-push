# 0014: Endpoint lookup, endpoint-restricted send and user purge

Applications need three per-device and per-user operations that 0.3.0 lacks: a settings page must know whether this browser is registered to the signed-in user, a "send a test notification" button must reach only this browser, and account deletion must remove the user's payloads and owner row in the same transaction as the rest of the account.

`subscriptions.get({ userId, endpoint })` reads one subscription by endpoint hash and test mode. It returns null unless the row belongs to `userId`, so a caller learns nothing about another user's registration. It returns status, push service, health and timestamps, never the endpoint or keys.

`notifications.send` and `sendRaw` accept an optional `endpoint`. The send creates at most one delivery, for that subscription, when it is active, unexpired and owned by the user; otherwise it returns null and claims no idempotency key, like a send without eligible subscriptions. An expired target is marked gone, as fan-out does. The notification stores `endpointHash`, not the endpoint, and idempotent replay compares it: the same key with a different or omitted endpoint raises `WEB_PUSH_IDEMPOTENCY_CONFLICT`. `sendBatch` takes no endpoint because an endpoint belongs to one user. Rejected: a separate `sendToSubscription` method, which would duplicate validation, idempotency and callbacks for a filter on the same fan-out.

`users.purge({ userId })` is a new `users` group and module. It increments the registration generation like `subscriptions.removeAll`, records the purge time, and deletes in steps of at most 100 rows: earlier-generation subscriptions, then notifications created at or before the purge time with their deliveries. A step that fills the bound schedules `users.continuePurge`. The last step deletes the `subscriptionOwners` row when the user has no subscription left. Rejected: a delivery index on `userId`, because a delivery never outlives its notification outside cleanup, which deletes deliveries before notifications; walking notifications needs no schema index.

Deleting the owner row reopens the hazard [0008](0008-subscription-attempts-and-removal.md) avoids: a later registration recreates the row at generation 0, and a removal continuation scheduled before the purge would delete registrations of a lower generation. Every removal and purge continuation therefore reads the owner row first and deletes subscriptions only when the row exists and its generation is at least the continuation's. A superseded continuation deletes a subset of what the current removal deletes, so it stays safe. Cleanup still never deletes owner rows.

Purge works in the client's resolved test mode, like every user read. Batch rows keep the user ID until cleanup deletes the batch. A delivery already running when its rows are deleted ends as `delivery_closed` without writes, and purged notifications never invoke `onNotificationComplete`.
